This release adds two opt-in features to the app bridge and the local library. One seals the state file at rest, and the other deletes an account. One change breaks Rust code: anyone who implements `BingleLocalApi` must add `delete_account`. The release also fixes a bug where a JavaScript reload left an old engine running, which could lose incoming messages.

## What changed

Six changes affect app builders or Rust integrators, and the rest are internal.

| Area | Change | Issue |
|---|---|---|
| App bridge (bingle_jsi) | The new `encrypt_state` config option seals the state file at rest. It is off by default and needs `key_storage: "keychain"`. At start-up, check `stateFileStatus()`. `locked` and `recovery_phrase_required` mean the file exists but hasn't opened, so don't treat it as a new user. `forgetStateKey()` handles the device locking, and `openStateWithRecoveryPhrase(phrase)` opens a file restored from a backup. | [#459](https://github.com/binglefoundation/bingle_rust/issues/459) |
| App bridge (bingle_jsi) | `deleteAccount()` opts the account out of the DApp (decentralized application) on chain. It then deletes the stored keys and the state file, and stops the engine. The Algorand account, its ALGO and its Bingle$ holding stay. A failure rejects with `BINGLE_ERROR`, and every cause is safe to retry. | [#100](https://github.com/binglefoundation/bingle_rust/issues/100) |
| App bridge (bingle_jsi) | A JavaScript reload no longer leaves the old engine running on the same account. Before, that engine confirmed incoming messages and then lost them. Stopping the bridge now also stops the backstop Mailbox poller. | [#456](https://github.com/binglefoundation/bingle_rust/issues/456) |
| Core library | `AlgoBingle::leave_app_lineage` clears the account's local state on the configured app and on every blessed ancestor app. This releases the handle, so importing the key again doesn't bring the old handle back. | [#100](https://github.com/binglefoundation/bingle_rust/issues/100) |
| Local library | `BingleLocalApi::delete_account` is new, and every implementor of the trait must add it. If the on-chain step fails, nothing on the device changes. | [#100](https://github.com/binglefoundation/bingle_rust/issues/100) |
| Local library | With `LocalApiConfig::encrypt_state` and the Keychain key store, `save` writes a sealed file instead of plain JSON (JavaScript Object Notation). An existing plain file is sealed on first load. `save` won't overwrite a file that hasn't opened. It returns `StateLocked` or `RecoveryPhraseRequired` instead. | [#462](https://github.com/binglefoundation/bingle_rust/issues/462) |
| Local library | The blockchain_ops_rust crates move to 0.9.7. Development builds now compile the vault and encryption crates with optimisation, so sealed saves in tests are about as fast as plain JSON. Release builds are unchanged. | [#462](https://github.com/binglefoundation/bingle_rust/issues/462) |
| Tests | The Android end-to-end harness now keeps its command state outside React. A recreated activity therefore still shows the result of a command that was running. A new test recreates the activity while a command runs. | [#431](https://github.com/binglefoundation/bingle_rust/issues/431) |
| CI (continuous integration) | The Android end-to-end job no longer runs its focus watcher, which stopped after one sample. A failing run now prints focus changes from the device events log. | [#454](https://github.com/binglefoundation/bingle_rust/issues/454) |
| Release process | The new `POST_RELEASE_CHECKS.md` lists checks that can only run after a release, such as on a device or on MainNet. `scripts/release.sh` prints them when it finishes. The first entry is the device check for this release's reload fix. | [#461](https://github.com/binglefoundation/bingle_rust/issues/461) |

## Upgrading

You only need to change code if you implement `BingleLocalApi`. Apps need code changes only to use the new features.

- **App (React Native):** Update to the new `react-native-bingle-jsi` and rebuild the native app, because the generated bindings have changed. To seal the state file:
  - Set `encrypt_state: true` with `key_storage: "keychain"`. Init refuses it with the file store.
  - Check `stateFileStatus()` at start-up.
  - Call `forgetStateKey()` on `protectedDataWillBecomeUnavailable`, and `load(path)` after `protectedDataDidBecomeAvailable`.
  - Ask for the recovery phrase when the status is `recovery_phrase_required`.
- **Rust users of bingle_core and bingle_local:** Implementors of `BingleLocalApi` must add `delete_account`. `KeyStore` also gains `holds_state_secret`, `state_secret` and `delete_state_secret`.
